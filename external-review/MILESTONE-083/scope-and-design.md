## The narrow claim this milestone builds

> A persisted M083 watermark binds one stable watermark identity to the exact
> set of M082 receipt governance identities visible to the schema-qualified
> PostgreSQL capture query executed by the statement that created the
> watermark, under that statement's own transaction snapshot. The set is
> stored in deterministic canonical order and does not change when later
> receipts are inserted, and ordinary row-level UPDATE/DELETE against that
> row is refused by the installed trigger (owner review REV-003: this is
> two bounded claims, not one absolute-immutability claim -- TRUNCATE, DROP,
> disabling the trigger, and superuser mutation remain outside it).

This does **not** claim any ResearchSession, DecisionCandidate, brief or
evaluation consumed the watermark. M070 decisions are produced across
multiple transactions and do not consume M082 receipts; M077 reads M076
independently through M079's operator-supplied `recorded_at` firewall.
Attaching today's receipt inventory to an already-completed decision would be
a post-hoc association, not evidence the decision used that set. M083 builds
the primitive a future evaluation-context milestone (not started) would need
to make that binding honestly.

## Candidate ranking

| Candidate | Verdict | Reason |
|---|---|---|
| A. receipt-label cutoff / maximum label | Rejected | Labels are unauthenticated (M082 authority) and carry no chronology; a cutoff selects, it does not attest completeness. |
| B. bigserial / max sequence / committed prefix | Rejected | No sequence column exists on `operator_event_receipt`, and assignment order is not commit order — a rollback gap is not missing evidence. Introducing one would add exactly the sequence authority Section 3 forbids. |
| C. application `list_all()` then a separate INSERT | Rejected | Two statements race: a receipt can commit between the read and the write, and a caller can trivially omit or add identities before the second statement. Completeness would rest on caller discipline, not the database. |
| D. caller-populated normalized membership rows | Rejected unless database-enforced | Without a mechanism forcing agreement with `operator_event_receipt`, a caller (or a bug) can persist a row that lies about its own membership. |
| **E. one database-computed row, exact set generated by PostgreSQL from one schema-qualified query during INSERT, row-level UPDATE/DELETE refused thereafter** | **Selected** | The BEFORE INSERT trigger computes and unconditionally overwrites `receipt_governance_ids` inside the same statement as the INSERT, so a direct SQL caller cannot influence the stored set by any combination of omission, addition, duplication or reordering — proven by execution, not argued (Section 8, attacks 9-13). |
| F. modify frozen M070/M076/M082 behaviour | Rejected | High frozen-contract risk, and even a successful change could only produce a post-hoc association, not genuine evidence-of-use — the wrong problem for M083 to solve. |

## Schema and enforcement

`evaluation_evidence_watermark(watermark_governance_id TEXT PRIMARY KEY,
receipt_governance_ids TEXT[] NOT NULL)`.

- **BEFORE INSERT** trigger `evaluation_evidence_watermark_capture_receipt_set`
  runs `SELECT COALESCE(array_agg(receipt_governance_id ORDER BY
  receipt_governance_id COLLATE "C"), ARRAY[]::text[]) FROM
  public.operator_event_receipt` and assigns it to `NEW.receipt_governance_ids`
  unconditionally — it never reads what the caller (or a direct INSERT
  statement) supplied for that column.
- Schema-qualified (`public.operator_event_receipt`), pinned
  `search_path = pg_catalog, public`, mirroring M082's own pg_temp-shadowing
  defence, and independently proven not to be shadowable (attack 13).
- `COLLATE "C"` is explicit in the query so canonical order does not depend on
  the database's default collation.
- Empty receipt table → `COALESCE(..., ARRAY[]::text[])`, an explicit `{}`,
  never NULL (the column is `NOT NULL`).
- **BEFORE UPDATE OR DELETE** trigger refuses both unconditionally — row-level
  immutability under the installed trigger only; TRUNCATE, DROP, disabling the
  trigger, and superuser mutation remain outside it, executed and proven in
  attack 32, not merely asserted.
- Primary key on `watermark_governance_id` is the whole idempotency mechanism:
  a second `capture()` call for an existing id reads back the existing row; a
  concurrent race on the same id is resolved by the database's unique
  constraint, and the repository reads the winner back rather than raising.

## Statement-snapshot visibility, precisely

Unlike M082's prior-committed-event trigger, M083 makes **no** prior-commit
claim. The capture query runs in the same transaction as the INSERT that
fires it, under ordinary PostgreSQL statement semantics: a statement sees the
effects of every earlier statement in **its own** transaction, committed or
not. Measured directly (attack 20): a receipt inserted earlier in the *same*
transaction as the watermark capture *is* included, even though it has not
committed. A receipt visible only in a different, still-open transaction is
excluded until that transaction commits (attack 17) and a receipt committed
after the capture statement's snapshot was taken is excluded from that
watermark, but may appear in a later one without mutating the earlier row
(attacks 18-19).

## Frozen contracts preserved

No M057, M070, M076, M077, M078, M079, M080, M081 or M082 domain, migration,
repository or authority file is modified. `operator_event_receipt` is read,
never written, by anything M083 adds. The M083 migration adds one table, two
trigger functions and two triggers; downgrade removes only those objects
(proven in attack 29 against a live database, not asserted).

## Independent database-design review (owner deep-closure mission)

Beyond the five numbered owner findings, a from-scratch review of the trigger
design against real PostgreSQL asked, and measured rather than assumed:

- **Isolation levels beyond the default.** The 33 original attacks measure
  READ COMMITTED (this milestone's actual, documented behaviour). Two
  further attacks measure the OTHER isolation levels PostgreSQL offers, not
  because M083 claims anything about them, but to be certain the capture
  trigger's behaviour under them is not silently wrong: under REPEATABLE
  READ a whole transaction holds ONE snapshot from its first statement, so a
  receipt committed after that snapshot is excluded even from a capture
  issued later in that same transaction — genuinely different from the
  default per-statement-snapshot behaviour attacks 18-19 already measure,
  and executed, not inferred. Under SERIALIZABLE, a real write-skew
  anomaly (two transactions each reading the table, then each writing a
  different row) was provoked and PostgreSQL's SSI genuinely aborted one
  side with SQLSTATE 40001; the loser's retry then succeeded. Neither
  observation changes the exact-set claim, which is stated only for the
  application's actual default (READ COMMITTED); both are recorded as
  validation evidence of correct behaviour under levels this milestone does
  not otherwise touch.
- **SQL surfaces beyond a single-row VALUES INSERT.** A multi-row INSERT and
  an `INSERT ... SELECT` were both executed: the capture trigger is `FOR
  EACH ROW`, so both fire identically and every row receives the complete,
  independently-correct set. `COPY ... FROM STDIN` was executed directly
  against the psycopg driver and fires the same row trigger.
- **Two caller-forgery shapes the original 33 did not cover:** an explicit
  empty array supplied while real receipts exist (still overwritten), and an
  explicit `NULL` supplied for a `NOT NULL` column (still overwritten,
  because a BEFORE ROW trigger runs before NOT NULL validation — PostgreSQL
  own semantics, not an M083 invention).
- **A named-schema `search_path` attack**, distinct from the existing
  `pg_temp` attack: a hostile schema holding a shadow `operator_event_receipt`
  table was explicitly prepended to `search_path` before the capture INSERT.
  The trigger's own `SET search_path = pg_catalog, public` pins its
  resolution regardless of the calling session's search_path, and the
  forged receipt identity never appeared in the stored set.
- **A real (not faked) unrelated-constraint propagation**: calling the
  repository directly with a blank identity (bypassing the Python-layer
  command validation that would normally refuse it first) reaches
  PostgreSQL's real `ck_evaluation_evidence_watermark_id_present` CHECK
  constraint (SQLSTATE 23514) rather than the unique-violation path
  `capture()`'s conflict handling is built for; `unique_violation_
  constraint_name` correctly returns `None` for it and the repository
  re-raises rather than misclassifying it as a winner conflict.
- **The exact column-length boundary**: 64 characters succeeds, 65 is
  rejected by the column type itself at the database boundary, independent
  of any Python-layer length check.

All of the above are committed as `tests/integration/test_m083_evaluation_
evidence_watermark_extended_attacks.py` (10 attacks, E1-E10), run repeatedly
against a live database with no failures. Full totals: `hostile-review.md`.

## Why not E-equivalent alternatives

An earlier internal draft considered exposing a digest (hash) of the receipt
set instead of, or alongside, the identities. Rejected per Section 5.10: a
digest is optional validation evidence at best; the identities are the
authority, and a digest would invite a caller to compare digests instead of
sets, silently narrowing what "exact" means.
